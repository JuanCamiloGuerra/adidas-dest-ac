Punto de partida

Dos piezas distintas,
dos responsabilidades

La API no fue inventada por nuestro análisis. El proveedor entregó un servidor mock con productos, usuarios y pedidos sintéticos. Nosotros construimos el cliente y el pipeline que convierte sus respuestas en información analítica.

02
La API original

Una puerta HTTP
hacia tres recursos

Una API es un contrato: el cliente formula una solicitud a una URL y el servidor responde con JSON. El pipeline oficial nunca abre directamente los archivos internos del proveedor.

GET/healthEstado y conteos.
GET/productsCatálogo paginado.
GET/products/{id}Detalle de producto.
GET/usersClientes paginados.
GET/users/{id}/cartsHistorial del cliente.
GET/cartsPedidos paginados.
Ejemplo interactivo

¿Qué le pedimos al servidor?

GET consulta información sin modificar el origen.

Respuesta del servidor● HTTP 200 · JSON
La respuesta paginadatotal indica cuánto existe; skip desde dónde leemos; limit cuánto pedimos; count cuánto llegó. La colección viaja en products, users o carts.



2.1
Cambios al servidor entregado
Cambiamos la operación,
no el significado
Conservamos endpoints, filtros y campos. Los ajustes hicieron la fuente reproducible y segura para desarrollo local.
Cambio 01
Ruta coherente
El generador escribía en output/ y el servidor buscaba en otra ubicación. Ahora ambos usan api/data/.
Cambio 02
Autogeneración
Si falta una colección, el servidor llama al generador. Un clon nuevo no depende de archivos ocultos.
Cambio 03
Reproducibilidad
random.seed(42) y Faker.seed(42) se reinician dentro de build_all().
Cambio 04
Acceso local
Se reemplazó 0.0.0.0 por 127.0.0.1 para no exponer la API a toda la red.
Cambio 05
Mantenimiento
Tipos, docstrings, paginación común, filtros con casefold() y errores consistentes.
Límite
No corregimos la fuente
Los nulos siguen en la API. La capa analítica los señala sin reescribir el dato original.

y demostrarlo
SportRetailAPIClient convierte “traer todos los pedidos” en solicitudes controladas y solo termina cuando el total queda reconciliado.
Se detiene ante HTTP distinto de 200, JSON inválido, claves ausentes, total cambiante o página vacía prematura.

Controles incorporados
Timeout · reintentos · contrato · conteos
El cliente reintenta fallos transitorios de GET, exige HTTP 200 y un objeto JSON, valida las claves de paginación, avanza por el número realmente recibido y guarda snapshots con source: REST API.
